## ldaps-init

`ldaps-init` discovers your domain controllers from the host's existing
configuration, fetches the CA chain, and writes a working `~/.ldaprc` so that
`ldapsearch`, `ldapwhoami`, and this application all work without per-command
flags.

```bash
sudo ldaps-init -v          # -v shows each discovery step
```

`sudo` is normally required because `/etc/sssd/sssd.conf` is root-only. Run
without it if your DCs come from `/etc/krb5.conf` instead.

### What it does

1. **Discovers DCs** from `/etc/sssd/sssd.conf` (`ad_server`, `ad_backup_server`,
   `ldap_uri`) and `/etc/krb5.conf` (`kdc` entries for the default realm).
   Comma- and space-separated lists are both accepted. Backup servers are placed
   last so failover reaches them only after every primary.
2. **Derives the base DN** from the Kerberos realm or AD domain
   (`ONID.OREGONSTATE.EDU` → `dc=onid,dc=oregonstate,dc=edu`). A short domain name
   carrying no suffix falls back to the DC hostname's domain part.
3. **Fetches the CA chain** from the first DC that answers on port 636. All DCs in
   a domain share an issuing CA, so one is enough.
4. **Binds as you** (`user@domain`) and searches for your full DN.
5. **Writes `~/.ldaprc`** with every DC on one `URI` line, the base DN, your
   `BINDDN`, and the CA path.
6. **Completes the trust chain** by appending the root CA published in AD
   (see [Certificate chains](#certificate-chains)).

### Usage

```
ldaps-init [-v] [-f] [-n] [user@domain]

  -v   verbose — show discovery, cert fetch, and bind steps
  -f   overwrite an existing rc file (otherwise it exits untouched)
  -n   skip the bind entirely; just write the config
```

The bind identity is the first argument, else `$LDAP_BIND_DN`, else
`<invoking-user>@<realm>`. A bare username is qualified with the discovered
domain, so `ldaps-init jsmith` becomes `jsmith@example.edu`.

### Under sudo

Running under `sudo` writes the config to **your** home directory, not root's,
and chowns the files back to you — so `sudo ldaps-init` can read a root-only
`sssd.conf` while still configuring your account. Only a genuine root login
(no `SUDO_USER`) targets `/root`.

### Passwords

The password is read from `~/.ldappass` if present, with trailing whitespace
stripped. Otherwise you are prompted, and — once the bind has actually
succeeded — offered the chance to save it at mode `600`. A password is never
saved before it is known to work.

An empty password is refused outright. A simple bind carrying a DN and an empty
password is an *unauthenticated bind* (RFC 4513 §5.1.2): AD returns success
while granting nothing, so it would otherwise look like a valid login.

### Environment

| Variable | Default | Purpose |
|---|---|---|
| `LDAPRC` | `<home>/.ldaprc` | Output rc file |
| `LDAP_CERT` | `<home>/.ldap-cert.pem` | CA bundle path |
| `LDAP_BIND_DN` | — | Bind identity (the positional argument wins) |
| `LDAP_PASS_FILE` | `<home>/.ldappass` | Password file |
| `KRB5_CONFIG` | `/etc/krb5.conf` | Kerberos config |
| `SSSD_CONF` | `/etc/sssd/sssd.conf` | SSSD config |

### Result

```
# Generated by ldaps-init on Tue Jul 21 14:53:16 UTC 2026
# Domain: onid   Realm: ONID.OREGONSTATE.EDU

URI ldaps://dc05.example.edu:636 ldaps://dc06.example.edu:636 ldaps://dc04.example.edu:636
BASE dc=onid,dc=oregonstate,dc=edu
BINDDN CN=jsmith,OU=Staff,DC=onid,DC=oregonstate,DC=edu
TLS_CACERT /home/jsmith/.ldap-cert.pem
TLS_REQCERT demand
TLS_PROTOCOL_MIN 3.3
```

`URI` takes a space-separated list on **one** line and clients fail over left to
right; separate `URI` lines do not accumulate. `BINDDN` is a *user-only*
ldap.conf option — valid in `~/.ldaprc`, ignored in a system `ldap.conf` — and it
means commands need no `-D`:

```bash
ldapsearch -x -y ~/.ldappass '(sAMAccountName=jsmith)'
```

## Certificate chains

AD typically presents **leaf + intermediate but not the root**. OpenLDAP's CLI
tools accept that partial chain, so `ldapsearch` works. Stricter TLS stacks —
Node, Java, Python — do not: they build to a self-signed root or fail with
`unable to get issuer certificate`. An internal AD root is also rarely in the
system trust store.

`ldaps-init` closes that gap by pulling the published root from the forest's
Configuration NC:

```
CN=Certification Authorities,CN=Public Key Services,CN=Services,<configurationNamingContext>
```

Note that this NC lives under the **forest root**, which may differ from your
domain — `DC=oregonstate,DC=edu` where the domain is `DC=onid,DC=oregonstate,DC=edu`.
It is read from the RootDSE rather than assumed. Expired generations of renewed
CA keys are dropped, since AD keeps every past generation.

Verify the resulting bundle:

```bash
openssl crl2pkcs7 -nocrl -certfile ~/.ldap-cert.pem | openssl pkcs7 -print_certs -noout | grep subject=
echo | openssl s_client -connect dc05.example.edu:636 -CAfile ~/.ldap-cert.pem 2>/dev/null | grep 'Verify return code'
# Verify return code: 0 (ok)
```

## Application authentication

The app verifies a password by binding to the directory as that user
(`src/server/auth/ldap-auth.ts`). Each attempt uses its own short-lived
connection — the shared `LdapClient` is bound as the service account, so
re-binding it as an end user would swap the identity out from under concurrent
requests.

| Variable | Purpose |
|---|---|
| `LDAP_AUTH_URL` | `ldaps://` URL for user authentication |
| `LDAP_CA_CERT` | CA bundle (the file `ldaps-init` wrote) |
| `LDAP_UPN_SUFFIX` | AD style: binds as `<login>@<suffix>` |
| `LDAP_BIND_DN_TEMPLATE` | e.g. `uid={login},ou=People,dc=example,dc=edu` |
| `REQUIRE_LOGIN` | `ldaps` forces directory-verified login only |

The bind identity is resolved in order: `bindDnTemplate`, `upnSuffix`, then a DN
lookup through the directory backend. Logins are restricted to `[A-Za-z0-9._-]`
rather than escaped per context, which closes DN- and filter-injection at once.

Only LDAP result code 49 (`invalidCredentials`) becomes a `401`; anything else is
a `503`, so an unreachable DC is never reported to a user as a wrong password.
The client always sees a generic message so the endpoint cannot enumerate
accounts. Session ids are regenerated on login.

### REQUIRE_LOGIN=ldaps

Suppresses **both** other ways in — the passwordless local-trust session and the
shared `config.yaml` admin account — leaving a successful LDAPS bind as the only
path to a session.

```bash
NODE_ENV=production DIRECTORY_BACKEND=nss REQUIRE_LOGIN=ldaps \
  LDAP_AUTH_URL=ldaps://dc05.example.edu:636 \
  LDAP_CA_CERT=~/.ldap-cert.pem LDAP_UPN_SUFFIX=example.edu \
  npm start
```

Because nothing remains to fall back to, a misconfiguration here does not
degrade — it locks everyone out. The server validates at startup and **exits
rather than serving a site nobody can enter** if the URL is not `ldaps://`, or if
the NSS backend is used without `upnSuffix` or `bindDnTemplate` (NSS synthesizes
a placeholder `uid=<name>` DN that cannot be bound with). A missing CA cert warns
rather than exits.

Note this also relaxes the loopback-only default that `AUTH_MODE=local`
otherwise forces, since requiring a login removes the risk that default guards
against. Set `BIND_HOST` explicitly if you still want loopback.

## Troubleshooting

**`ldapsearch: command not found`**
Ubuntu/Debian: `apt-get install ldap-utils openssl` · RHEL/Alma:
`yum install openldap-clients openssl`

**`no DCs found; /etc/sssd/sssd.conf needs root`**
Run `sudo ldaps-init`. Confirm the file has servers:
`sudo grep -E 'ad_server|ldap_uri' /etc/sssd/sssd.conf`

**`unable to get issuer certificate` (Node/Java/Python, but `ldapsearch` works)**
The CA bundle has the intermediate but not the root. Re-run `ldaps-init -f` to
append the published root; see [Certificate chains](#certificate-chains).

**`Invalid credentials` for a password you know is right**
Check the bind identity form. AD accepts `user@domain` (UPN); a bare username
usually fails. Verify directly:
```bash
LDAPTLS_CACERT=~/.ldap-cert.pem ldapwhoami -x -H ldaps://dc05.example.edu:636 \
  -D "jsmith@example.edu" -y ~/.ldappass
```

**`REQUIRE_LOGIN=ldaps cannot be satisfied`**
The startup check is refusing a config that would lock everyone out. The message
names the specific problem — fix it rather than removing the variable.
